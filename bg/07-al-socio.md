# Урок 07 — Към партньора

> **Какво ще постигнеш:** да оставиш 850-ката от урок 06 в пощенската кутия на търговския партньор с четири предпазни мерки: той да не взима
> файл наполовина, една и съща поръчка винаги да има едно и също име, второ изпращане да не изтрива първото и маршрутът да се свързва само със сървъра, чийто ключ е в `known_hosts`.

**Преди да започнеш, ти трябват:** завършен урок 06 и включена средата от урок 00:

```bash
docker compose -f infra/compose.yaml up -d --wait     # desde la carpeta raíz de la práctica
```

## Новото днес, в едно изречение

Партньорът няма API: има **SFTP пощенска кутия** — папка на своя сървър, в която ти качваш файлове и от
която той ги чете, **когато поиска**. Не те уведомява кога чете и не ти отговаря. Затова това, което оставяш там, трябва да е
цяло и не бива да пречи на вече наличното.

**SFTP, най-необходимото:** програма за сигурно копиране на файлове на друг компютър през мрежата. Иска потребител
и парола (или ключ) и преди да се свърже, проверява, че сървърът е този, за който се представя. Тази проверка
е стъпка 2.

## 1. Подготви папката си

```bash
cd lecciones/07-al-socio
cp -R inicio mio
cd mio
```

Маршрутът използва мапинга и шаблона на 850-ката от урок 06, които вече са вътре в `mio/`.

## 2. Довери се на партньора

Първия път, когато говориш с един сървър, трябва да знаеш, че е **този на партньора ти**, а не друг, който се представя за
него. Всеки сървър има **публичен ключ**, нещо като пръстов отпечатък. Записваш го веднъж във файл с име
`known_hosts` и оттогава маршрутът се свързва само ако сървърът представи същия ключ.

```bash
../../../herramientas/confiar-en-socio
```

В реалния живот партньорът ти праща ключа си по друг канал (имейл, портал) и ти го записваш на ръка. Тук
скриптът го взема направо от контейнера на партньора, който играе ролята на негов администратор.

⚠️ Ако изключиш средата с `down` и я вдигнеш отново, сървърът на партньора получава нов ключ: пусни пак
скрипта. `known_hosts` е твой и git не го следи.

## 3. Прочети маршрута

Отвори `orden-al-socio.camel.yaml`. Това е маршрутът от урок 06 с друга изходна гара:

```yaml
uri: sftp://socio@socio-sftp:22/entrada
```

| Част | Какво е |
|---|---|
| `socio@` | Потребителят, с който влизаш в пощенската кутия |
| `socio-sftp:22` | Сървърът на партньора и неговият порт |
| `/entrada` | Папката, от която партньорът прибира това, което му пращат |

Отдолу са параметрите му:

| Параметър | Какво прави |
|---|---|
| `knownHostsFile: known_hosts` и `strictHostKeyChecking: "yes"` | Свързва се само ако ключът на сървъра е този, който записа в стъпка 2 |
| `fileName: "850-${variable.orden}.edi"` | Окончателното име. Поръчка 1001 винаги се казва `850-1001.edi` |

Такова име се нарича **детерминистично**: зависи само от поръчката. Ако носеше часа или случайно число,
една и съща поръчка, пратена два пъти, би оставила два файла и партньорът би я изпълнил два пъти.

## 4. Предвиди

Отговори на лист хартия:

1. Ако пратиш поръчка 1001 два пъти, колко файла очакваш в пощенската кутия на партньора?
2. Ако втория път поръчката носи **друго количество** (5 чаши вместо 2), какво съдържа файлът накрая?
3. Ако някой смени сървъра на партньора с друг, с друг ключ, какво според теб прави маршрутът?

## 5. Пусни го два пъти

Сложи поръчка 1001 в `entrada/` и пусни маршрута. `--max-messages=1` го спира сам след една поръчка:

```bash
mkdir -p entrada
cp ../../../datos/ordenes/orden-1001.json entrada/
../../../herramientas/camel run orden-al-socio.camel.yaml --max-messages=1
```

Попитай пощенската кутия на партньора какво има в нея:

```bash
docker compose -f ../../../infra/compose.yaml exec socio-sftp ls /home/socio/entrada
docker compose -f ../../../infra/compose.yaml exec socio-sftp cat /home/socio/entrada/850-1001.edi
```

Сега прати **същата поръчка с друго количество**, `orden-1001-cambiada.json`, и погледни пак пощенската кутия:

```bash
cp ../../../datos/ordenes/orden-1001-cambiada.json entrada/
../../../herramientas/camel run orden-al-socio.camel.yaml --max-messages=1
docker compose -f ../../../infra/compose.yaml exec socio-sftp cat /home/socio/entrada/850-1001.edi
```

Намери първия `PO1`. Казва `PO1*1*5*…`: **второто изпращане изтри първото, без да предупреди**. Има един-единствен файл, както
предвиди във въпрос 1, но това вече не е поръчката, която партньорът имаше. Ако вече я е прочел, сега има две
различни версии на поръчка 1001 и не знае коя важи.

## 6. Добави двете мерки, които липсват

В маршрута има коментар **TE TOCA**. Там отиват още два параметъра на гарата `sftp:`:

**Временно име.** Качването на файл отнема време. Ако партньорът прочете папката си точно по средата, ще вземе
отрязан файл. Решението е да го запишеш с друго име и да го смениш накрая, което става мигновено:

```yaml
tempFileName: "${file:onlyname.noext}.tmp"
```

Докато се записва, се казва `850-1001.tmp`; когато приключи, се преименува на `850-1001.edi`. Ако партньорът прибира само
`.edi` файлове, е много трудно да вземе непълен: преименуването е последното, което се случва. Това не е пълна
гаранция (партньор, който прибира всякакви файлове, или зле конфигурирана споделена папка я развалят) и затова в
урок 21 потвърждението, че е пристигнало добре, го дава 997, а не файлът.

**Без презаписване.** По подразбиране, ако файлът вече съществува, Camel го заменя. Ти искаш обратното: да се провали и някой
да реши.

```yaml
fileExist: Fail
```

Внимавай с отстъпа: двата са на същото ниво като `fileName`.

Изпразни пощенската кутия и повтори стъпка 5:

```bash
docker compose -f ../../../infra/compose.yaml exec socio-sftp rm /home/socio/entrada/850-1001.edi
```

Сега второто изпращане не минава. В терминала на маршрута се появява:

```
File already exist: entrada/850-1001.edi. Cannot write new file.
```

А променената поръчка **остана в твоята папка `entrada/`**, без да се отдели в `.camel/` като тези, които минават успешно. Не се
е загубила: чака някой да реши какво да прави с нея. Това ще го решиш в урок 18.

## 7. Смени ключа

Сега въпрос 3. Направи резервно копие на своя `known_hosts`, сложи фалшив ключ и прати една поръчка:

```bash
cp known_hosts known_hosts.bueno
echo "socio-sftp ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIHVuYWxsYXZlZGVvdHJvc2Vydmlkb3JxdWVub2Vz" > known_hosts
cp ../../../datos/ordenes/orden-1003.json entrada/
../../../herramientas/camel run orden-al-socio.camel.yaml --max-messages=1 --max-seconds=40
```

Сред грешките ще намериш:

```
HostKey has been changed: socio-sftp
```

Маршрутът **отказа да се свърже**: сървърът представи ключ, различен от записания. Може партньорът да го е
сменил (и би трябвало да те уведоми по друг канал), а може някой да е по средата и да се представя за него. И в двата
случая правилното е да не му пращаш нищо. Върни добрия си ключ:

```bash
mv known_hosts.bueno known_hosts
```

## 8. Провери

```bash
cd ..
./verifica
```

⚠️ `verifica` **изпразва пощенската кутия на партньора**, преди да тества.

Урокът е завършен, когато видиш седемте зелени отметки:

```
✅ Llegó 850-1001.edi al SFTP del socio
✅ No quedó ningún archivo .tmp
✅ Lo que recibió el socio es el 850 correcto
✅ Un segundo envío de la 1001 no pisó el archivo que ya estaba
✅ La ruta escribe con nombre temporal
✅ La ruta intentó conectar y el servidor no presentó la llave anotada
✅ Con otra llave en known_hosts, la ruta se negó a conectar
```

Петата е различна от останалите: `.tmp` живее няколко милисекунди и няма как да се види отвън, затова
`verifica` го проверява в твоя маршрут. Шестата търси в лога `HostKey has been changed` от стъпка 7: доказва, че
маршрутът наистина се е опитал да се свърже и че го е отхвърлил ключът, а не друга повреда. Останалите ги потвърждава пощенската кутия на партньора.

**Не тръгва?** `./verifica solucion` тества нашето решение, а
`diff mio/orden-al-socio.camel.yaml solucion/orden-al-socio.camel.yaml` ти казва по какво се различават.

| Какво виждаш | Какво правиш |
|---|---|
| `PISÓ el archivo del socio` | Липсва `fileExist: Fail` |
| `no usa nombre temporal` | Липсва `tempFileName` |
| `HostKey has been changed` при всички пускания | Пресъздал си средата: пусни отново `confiar-en-socio` (стъпка 2) |
| `No pude hablar con el SFTP del socio` | Включи средата: `docker compose -f infra/compose.yaml up -d --wait` |
