# Урок 08 — Рутерът

> **Какво ще постигнеш:** да разделиш интеграцията си на две услуги, които работят отделно: един **рутер**, който получава
> поръчката, и една услуга **int-rest**, която знае как да говори с API-то. Пишеш извикването, което ги свързва — по името
> на услугата и никога по адрес.

**Преди да започнеш, ти трябват:** завършени уроци от 02 до 07 и включена средата от урок 00:

```bash
docker compose -f infra/compose.yaml up -d --wait     # desde la carpeta raíz de la práctica
```

## Новото днес, в едно изречение

Досега всеки урок беше **един** маршрут, който прави всичко: получава, превежда и доставя. С три дестинации (API-то,
ERP и партньора) този маршрут би растял без край. Днес го разделяш: една услуга **решава къде отива** поръчката, а друга **знае
как да я достави**. Всяка работи в собствен контейнер.

```
tienda ──POST /ordenes──▶ [orden-router] ──POST http://int-rest:8080/integrar──▶ [int-rest] ──▶ API de pedidos
```

**Картината:** регистратурата на болница. Регистраторката не оперира никого: пита какво ти е и те праща при
специалиста. Ако утре се открие нова специалност, регистратурата остава същата; само научава още една врата.

## 1. Подготви папката си

```bash
cd lecciones/08-el-router
cp -R inicio mio
```

Виж какво копира: `mio/` има **две папки**, по една за услуга.

| Папка | Услуга | Какво носи |
|---|---|---|
| `mio/orden-router/` | Рутерът | Неговия маршрут: получава поръчката от магазина и я подава на int-rest |
| `mio/int-rest/` | int-rest | Неговия маршрут и мапинга v2 от урок 03: превежда поръчката и я доставя на API-то |

## 2. Прочети compose файла на урока

Този урок не използва `herramientas/camel`. Двете услуги се вдигат заедно със собствен `compose.yaml`, както
средата от урок 00. Отвори го:

```yaml
x-camel: &camel
  image: apache/camel-jbang:4.22.1
  command: ["run", "."]          # corre todos los *.camel.yaml de su carpeta

services:
  orden-router:
    <<: *camel
    volumes:
      - ./${DONDE:-mio}/orden-router:/work
    ports: ["8080:8080"]

  int-rest:
    <<: *camel
    volumes:
      - ./${DONDE:-mio}/int-rest:/work
    # sin ports: no se ve desde tu máquina; por dentro de la red, cualquier servicio lo alcanza
```

Две неща, които си струва да видиш:

- **Двете услуги са един и същ образ на Camel.** Единственото различно е папката, която всяка монтира. `&camel`
  дефинира общата част веднъж, а `<<: *camel` я използва повторно. За да създадеш нова услуга, не е нужно да програмираш друга
  програма: стига още една папка с маршрутите ѝ.
- **Само рутерът има `ports`.** Той е единственият, който се вижда от твоята машина. int-rest не се вижда отвън, но
  вътре в мрежата на Docker всяка услуга може да го извика; в този курс единственият, който го вика, е рутерът.

`DONDE` е променлива, която казва кои папки да се монтират: `mio` (твоята, по подразбиране) или `solucion` (нашата).

## 3. Прочети двата маршрута

**`mio/int-rest/int-rest.camel.yaml`** идва завършен. Получава на `/integrar`, превежда с мапинга v2 и вика
API-то, също като маршрута от урок 03.

**`mio/orden-router/orden-router.camel.yaml`** получава на `/ordenes` и подготвя поръчката, за да я подаде нататък. Преди
извикването ѝ слага няколко хедъра, които започват с `ce-`:

| Хедър | Стойност за поръчка 1003 |
|---|---|
| `ce-specversion` | `1.0` |
| `ce-type` | `mx.tienda.orden.creada` |
| `ce-source` | `/tiendas/T-022` |
| `ce-subject` | `1003` |
| `ce-id` | `orden-1003-creada` |

Те са **пликът** на поръчката, в стандартен формат, който се казва **CloudEvents**: казват какво се е случило, къде и на кого.
Днес само ще ги **гледаш** как пътуват; в урок 09 те служат, за да проследиш една поръчка от услуга на услуга.

В края на маршрута има един **TODO**: липсва извикването към int-rest.

## 4. Предвиди

Преди да напишеш извикването, отговори на лист хартия:

1. Ако пратиш поръчка 1003 на рутера такъв, какъвто е, без извикването, какво отговаря той на магазина? Стига ли нещо до
   API-то?
2. Когато извикването вече е налице, в каква последователност очакваш да видиш как поръчката минава през логовете на двете услуги?
3. Вътре в контейнера на рутера към коя машина според теб сочи `localhost`?

## 5. Напиши извикването

На мястото на TODO добави стъпка `to`, която прави `POST` към маршрута `/integrar` на int-rest, на неговия порт 8080.
Извикай го **по името на услугата**, `int-rest`, както int-rest вика API-то по `api-pedidos`. Използвай
`throwExceptionOnFailure: false`, за да може, ако int-rest отговори с грешка, рутерът да я запише, вместо да се провали:
следващият ред от лога казва какво е отговорил.

Ако заседнеш, извикването от int-rest към API-то има точно същата форма.

## 6. Вдигни го и му прати една поръчка

От папката на урока:

```bash
DONDE=mio docker compose -f compose.yaml up -d
DONDE=mio docker compose -f compose.yaml logs -f
```

Втората команда показва логовете на двете услуги заедно, всеки ред с името на този, който го е написал.
Изчакай да видиш `Started orden-router` и `Started int-rest`. В **друг** терминал, от основната папка на курса:

```bash
curl -i -XPOST localhost:8080/ordenes -H 'Content-Type: application/json' -d @datos/ordenes/orden-1003.json
```

В логовете трябва да видиш как поръчката минава през двете услуги:

```
orden-router-1  | Orden 1003: se la paso a int-rest
int-rest-1      | Recibí del router la orden 1003 (sobre orden-1003-creada, tipo mx.tienda.orden.creada)
int-rest-1      | La API contestó 201 para la orden 1003
orden-router-1  | Orden 1003: int-rest contestó 201
```

Съвпада ли с предвиждане 2? Отговорът се връща по същия път: API-то отговаря на int-rest, int-rest — на
рутера, а рутерът — на магазина.

Ако API-то отговори с `200` вместо с `201`, то вече е имало поръчка 1003 от урок 03. Рестартирай го, за да започне празно:
`docker compose -f infra/compose.yaml restart api-pedidos`.

## 7. Счупи го нарочно: localhost

Сега въпрос 3. В маршрута на рутера смени `int-rest` с `localhost`:

```yaml
uri: http://localhost:8080/integrar
```

Изключи и вдигни отново услугите, за да вземат промяната, и прати поръчката още веднъж:

```bash
DONDE=mio docker compose -f compose.yaml down
DONDE=mio docker compose -f compose.yaml up -d
```

Магазинът получава **404**, а логът на рутера казва `int-rest contestó 404`. Но int-rest изобщо не е получил нищо.
**Вътре в контейнер `localhost` е самият този контейнер.** Рутерът извика сам себе си, потърси маршрут
`/integrar`, какъвто той няма, и си отговори „не съществува“. На твоята машина `localhost` е твоята машина; във всеки контейнер
е самият контейнер.

Затова услугите се викат по **име**: Docker знае в кой контейнер живее `int-rest`, дори утре
да си смени адреса. Върни името и изключи:

```bash
DONDE=mio docker compose -f compose.yaml down
```

## 8. Провери

```bash
./verifica
```

`verifica` рестартира API-то, за да започне празно, вдига двете услуги, праща поръчка 1003 и накрая ги
изключва. Урокът е завършен, когато видиш шестте зелени отметки:

```
✅ El router arrancó
✅ int-rest arrancó (la misma imagen, otra carpeta)
✅ La tienda mandó la 1003 al router y la respuesta final fue 201
✅ La API registró la orden 1003: el recorrido tienda → router → int-rest → API se completó
✅ int-rest recibió el sobre CloudEvents de la orden (id orden-1003-creada)
✅ int-rest no se ve desde tu máquina: solo el router lo alcanza
```

Четвъртата я потвърждава API-то от собствения си регистър: не стига рутерът да каже, че е подал поръчката.

**Не тръгва?** `./verifica solucion` тества нашето решение, а
`diff mio/orden-router/orden-router.camel.yaml solucion/orden-router/orden-router.camel.yaml` ти казва по какво се
различават.

| Какво виждаш | Какво правиш |
|---|---|
| `La tienda esperaba 201 y le llegó 200` | Рутерът е върнал поръчката, без да извика никого: липсва стъпката `to` |
| `La tienda esperaba 201 y le llegó 404` | Извикването сочи към `localhost`: върни се на стъпка 7 |
| `El puerto 8080 está ocupado` | Останал е друг работещ маршрут или услугите от този урок: `DONDE=mio docker compose -f compose.yaml down` |
| `El router no arrancó` | `verifica` показва последните редове от лога: почти винаги е отстъпът на новата стъпка |
